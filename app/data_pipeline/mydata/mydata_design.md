# 마이데이터 가상 데이터 설계서

> 목적: 주택구매 금융컨설팅 서비스의 Mock 마이데이터 생성 규격
> 기준: 금융분야 마이데이터 표준API 규격 v2 (2025-09-30), [첨부3] 계좌구분 코드, [첨부4] 상환방식 코드
> 담당 범위: **가상 데이터 생성 및 포맷 설계까지.** 생성된 데이터로 수행하는 계산(월 상환액, DSR, LTV 등)은 역할 1(백엔드)의 업무

---

## 1. 설계 원칙

### 1.1 표준 API 응답 형식을 그대로 흉내 낸다

Mock의 출력은 **실제 마이데이터 API가 회신하는 JSON과 구조·필드명·타입이 동일**해야 한다. 내부 편의를 위한 필드를 추가하지 않는다.

이유: 설계안의 Provider 교체 구조(`Mock → CSV → Sandbox → Production`)가 성립하려면, 정규화 계층이 읽는 입력이 항상 같아야 한다. Mock에만 있는 필드를 정규화 계층이 참조하는 순간 실연동 시 코드를 고쳐야 한다.

### 1.2 계산 결과를 데이터에 넣지 않는다

월 상환액, DSR, 가용자산 합계 등은 **역할 1이 계산할 값**이다. Mock은 그 계산의 **입력**만 제공한다.

| 넣는다 | 넣지 않는다 |
|---|---|
| `balance_amt` (대출잔액) | 월 상환액 |
| `last_offered_rate` (금리) | 연간 원리금 상환액 |
| `exp_date` (만기일) | DSR 값 |
| `repay_method` (상환방식 코드) | 잔여 개월수 |
| 개별 거래 내역 | 월별 소득 합계 |

### 1.3 계산 가능성을 보장한다

역할 1이 필요한 계산을 할 수 있도록, **입력 필드가 빠짐없이 채워져 있어야** 한다. 특히 규격상 `필수=N`인 필드라도 계산에 필요하면 채운다.

예: `unredeemed_start`/`unredeemed_end`는 규격상 선택이지만, 거치기간 대출 페르소나를 만들려면 반드시 채워야 한다.

### 1.4 시나리오는 역산으로 만든다

"월 상환액 120만원인 주담대"를 만들고 싶다면, 그 값이 나오도록 `balance_amt`·`last_offered_rate`·`exp_date`를 정한다. 역산 과정은 생성 스크립트 내부에만 존재하고, 출력 JSON에는 남기지 않는다.

검증 방법: 거래내역(은행-004)에 동일 금액의 자동이체 출금을 심어두면, 역할 1의 계산값과 대조할 수 있다.

## 3. 공통 포맷 규칙

### 3.1 타입 표기 대응

| 규격 표기 | 의미 | JSON 표현 | 예시 |
|---|---|---|---|
| `A(n)` | 영문자 n자 | string | `"KRW"` |
| `aN(n)` | 영숫자 n자 | string | `"1001"` |
| `AN(n)` | 영숫자 n자 | string | `"20260724000000001"` |
| `aNS(n)` | 영숫자+특수문자 | string | `"eyJhbGci..."` |
| `AH(n)` | 전체 문자(한글 포함) | string | `"KB국민 주거래 우대통장"` |
| `N(n)` | 숫자 n자 | string 또는 number | `"202607"` |
| `F(m,d)` | 실수, 소수 d자리 | number | `30000000.000` |
| `DATE` | `YYYYMMDD` | string | `"20250315"` |
| `DTIME` | `YYYYMMDDhhmmss` | string | `"20250315143022"` |
| `Boolean` | 참/거짓 | boolean | `true` |

### 3.2 코드값은 반드시 문자열

`account_type`, `trans_type`, `repay_method`, `saving_method`는 **앞자리 0이 의미를 가지므로 문자열로 저장**한다.

```json
"trans_type": "03"     ← 올바름
"trans_type": 3        ← 잘못됨 (03과 3이 구분 안 됨)
```

### 3.3 금액 필드

규격은 `F(18,3)`이지만 원화는 소수점이 무의미하다. **정수로 생성하되 JSON number 타입**으로 둔다.

```json
"balance_amt": 30000000
```

역할 1이 Decimal로 받을 수 있도록 하려면, 팀 합의에 따라 문자열(`"30000000.000"`)로 바꿀 수 있다. **어느 쪽이든 전체 파일에서 일관되어야 한다.**

### 3.4 금리 필드 — 단위 합의 필요

규격 `F(7,5)`는 자릿수만 정하고 단위는 명시하지 않는다. 두 해석이 가능하다.

| 해석 | 연 3.5%의 표현 |
|---|---|
| 소수 | `0.03500` |
| 퍼센트 | `3.50000` |

**본 설계서는 소수(`0.035`)를 채택한다.** 역할 1과 반드시 사전 합의하고, README에 명시한다. 이 합의가 어긋나면 DSR이 100배 틀린다.

### 3.5 미회신 필드 처리

규격상 "회신 안 함"인 경우는 **키 자체를 생략**한다. `null`을 넣지 않는다.

```json
// 만기 없는 자유입출금 계좌
{
  "saving_method": "01",
  "issue_date": "20200315"
  // exp_date 키 없음
}
```

이유: 실제 API가 키를 생략하므로, 정규화 계층이 `None` 대신 `KeyError`를 처리하도록 훈련시켜야 한다.

### 3.6 응답 래퍼

모든 응답에 공통 필드를 포함한다.

```json
{
  "rsp_code": "00000",
  "rsp_msg": "정상",
  "search_timestamp": "20260724120000",
  ...
}
```

`rsp_code` 정상값은 규격에서 확인되지 않았다. `"00000"`으로 가정하고 TODO로 표기한다.

## 4. 은행-001 계좌 목록 — 설계

### 4.1 필드 포맷

| 필드 | 타입 | 생성 규칙 |
|---|---|---|
| `rsp_code` | string | `"00000"` 고정 |
| `rsp_msg` | string | `"정상"` 고정 |
| `search_timestamp` | string N(14) | 생성 시각 `YYYYMMDDhhmmss` |
| `reg_date` | string DATE | 최초 거래일보다 이전. 예: `"20180301"` |
| `account_cnt` | number | `account_list` 길이와 일치 |
| `account_list[]` | array | 아래 |
| `.account_num` | string aN(20) | 숫자 문자열, `-` 없음. 기관별 자릿수 다름 (예: 14자리) |
| `.is_consent` | boolean | 전부 `true` (전송요구 동의한 계좌만) |
| `.seqno` | — | **생성하지 않음** (일반 은행은 미회신) |
| `.is_foreign_deposit` | boolean | 수신계좌만 `false`. 대출계좌는 키 생략 |
| `.prod_name` | string AH(300) | 실제 상품명 스타일 |
| `.is_minus` | boolean | 수신계좌만. 마이너스통장이면 `true` |
| `.account_type` | string aN(4) | [첨부3] 코드 |
| `.account_status` | string aN(2) | `"01"` 고정 |

### 4.2 account_type 선택 가이드

**수신 (필수 구성)**

| 코드 | 유형 | 페르소나별 필요성 |
|---|---|---|
| `1001` | 자유입출식 | **모든 페르소나 필수** (급여 입금·생활비 출금 계좌) |
| `1002` | 예금 | 목돈 보유 페르소나 |
| `1003` | 적금 | 저축 습관 있는 페르소나 |
| `1999` | 기타 | **주택청약저축을 여기 또는 1003에** |

**대출 (페르소나별 선택)**

| 코드 | 유형 | 용도 |
|---|---|---|
| `3100` | 신용대출 | DSR 부담 시나리오 |
| `3150` | 학자금대출 | 사회초년생 페르소나 |
| `3170` | 전세자금대출(신용) | 전세 거주 페르소나 |
| `3220` | 주택담보대출 | 기존 주택 보유 페르소나 |
| `3245` | 보금자리론 | 정책대출 페르소나 |
| `3270` | 전세자금대출(보증서) | 전세 거주 (보증서 방식) |
| `3500` | 신차 할부금융 | 자동차 부채 페르소나 |

> **청약 주의**: [첨부3]에 주택청약종합저축 전용 코드가 없다. `1003` 또는 `1999`로 만들되, `prod_name`에 반드시 **"청약"** 문자열을 포함시킨다. 역할 1이 청약을 주택구매 가용자산에서 분리하려면 이 문자열이 유일한 단서다.

> **전세대출 주의**: 신용(`3170`)과 보증서(`3270`, `3271`)로 갈라져 있다. 두 유형을 모두 테스트하려면 페르소나를 나눠 만든다. DSR 포함 여부가 보증 방식에 따라 다르므로 역할 1의 분기 테스트에 필요하다.

## 6. 은행-003 수신계좌 추가정보 — 설계

### 6.1 필드 포맷

| 필드 | 타입 | 생성 규칙 |
|---|---|---|
| `detail_cnt` | number | 원화 계좌는 `1` |
| `detail_list[]` | array | 길이 1 |
| `.currency_code` | string A(3) | `"KRW"` |
| `.balance_amt` | number | **자산 금액** |
| `.withdrawable_amt` | number | `balance_amt` 이하 |
| `.offered_rate` | number F(7,5) | 소수 표기 (3.5% → `0.035`) |
| `.last_paid_in_cnt` | number | 적금만. 해당 없으면 키 생략 |

### 6.2 값 설계 가이드

**`withdrawable_amt` < `balance_amt`인 케이스를 반드시 하나 이상 만든다.** 예금담보대출이 걸린 계좌를 표현할 수 있고, 역할 1이 "가용자산"을 판단할 때 어느 필드를 쓰는지 검증할 수 있다.

```
정기예금 5,000만원 중 2,000만원이 담보로 묶인 경우
  balance_amt: 50000000
  withdrawable_amt: 30000000
```

**금리 범위** (2026년 기준 현실적 값)

| 상품 | `offered_rate` |
|---|---|
| 자유입출식 | `0.001` ~ `0.005` |
| 정기예금 | `0.028` ~ `0.038` |
| 적금 | `0.030` ~ `0.045` |
| 청약저축 | `0.020` ~ `0.025` |

**마이너스통장 잔액은 음수**로 생성한다.

```json
{ "balance_amt": -8000000, "withdrawable_amt": 0, "offered_rate": 0.058 }
```

> ⚠ **한도 정보 부재 문제**: DSR 산정에서 마이너스통장은 "약정 한도 전액"을 기준으로 하는데, **표준 API에 한도 필드가 없다.** 은행-009의 `loan_principal`(대출원금)을 한도로 해석할 수 있는지 역할 1과 합의가 필요하다. 본 설계서는 `loan_principal`에 약정 한도를 넣는 방식을 채택한다(→ 8.3 참조).

## 7. 은행-004 거래내역 — 설계 (가장 중요)

소득·지출 데이터가 전부 여기서 나온다. **가장 공들여 만들어야 하는 파일이다.**

### 7.1 필드 포맷

| 필드 | 타입 | 생성 규칙 |
|---|---|---|
| `trans_cnt` | number | `trans_list` 길이 |
| `next_page` | string | 마지막 페이지면 **키 생략** |
| `trans_list[]` | array | **거래일시 내림차순 정렬** |
| `.trans_dtime` | string DTIME | `YYYYMMDDhhmmss` |
| `.trans_no` | string aN(64) | 일자별 일련번호 |
| `.trans_type` | string aN(2) | 아래 표 |
| `.trans_class` | string AH(15) | `"인터넷뱅킹"`, `"창구"`, `"ATM"`, `"자동이체"`, `"체크카드"` |
| `.currency_code` | string A(3) | `"KRW"` |
| `.trans_amt` | number | **항상 양수** (방향은 `trans_type`이 결정) |
| `.balance_amt` | number | **거래 후 잔액. 시계열 정합성 필수** |
| `.paid_in_cnt` | number | 적금 납입 회차. 해당 없으면 키 생략 |

### 7.2 trans_type 사용 방침

| 코드 | 의미 | Mock 사용 |
|---|---|---|
| `01` | 신규 | 계좌 개설 시 1건 |
| `02` | 출금 | **주력 (지출)** |
| `03` | 입금 | **주력 (소득)** |

### 7.3 `balance_amt` 시계열 정합성

**가장 흔한 Mock 오류**다. 거래 후 잔액이 앞뒤로 맞아야 한다.

```
생성 방법: 시간 오름차순으로 잔액을 누적 계산한 뒤, 출력 시 내림차순으로 뒤집는다

  잔액 = 시작잔액
  for 거래 in 시간순:
      if 입금계열: 잔액 += trans_amt
      if 출금계열: 잔액 -= trans_amt
      거래.balance_amt = 잔액
  최종 잔액 == 은행-003의 balance_amt   ← 반드시 일치
```

**은행-003의 `balance_amt`와 거래내역 마지막 잔액이 일치해야 한다.** 불일치하면 역할 1이 어느 쪽을 믿을지 판단할 수 없다.

### 7.4 `trans_memo` 설계 — 분류 가능성 확보

## 9. 사용자 직접 입력 데이터

마이데이터 범위 밖이지만 계산에 필요한 값이다. **별도 파일로 분리**한다.

```json
{
  "birth_year": 1992,
  "marital_status": "married",
  "household_size": 2,
  "is_first_home_buyer": true,
  "owns_property": false,
```

|---|---|

| `marital_status` / `household_size` | 신혼부부 특례, 부부 소득 합산 |

| `annual_income_verified` | **DSR 분모.** 거래내역 합계와 다를 수 있음(인정소득 기준) |
| **`planned_expenses`** | **설계안 7.4 "예정지출 적립액". 미래 계획이라 거래내역에서 도출 불가** |

## 10. 페르소나 설계

### 10.1 권장 4종

| A | 사회초년생 | 자유입출식 + 청약 + 학자금대출(`3150`, `04`) | 자산 부족, 청약 분리 |
| B | 신혼부부 (전세) | 자유입출식×2 + 적금 + 청약 + 전세대출(`3170`, `01`) | 만기일시 계산, 부부 합산 |

### 10.2 페르소나별 필수 검증 포인트

| 검증 항목 | 해당 페르소나 |

- [ ] `issue_date` <= 거래내역 최초 거래일
- [ ] `unredeemed_start` < `unredeemed_end`
- [ ] 대출 `balance_amt` <= `loan_principal` (한도거래 제외)
- [ ] 대출 상환액 자동이체 기록이 거래내역에 존재하는가

### 11.4 코드값 유효성

- [ ] `account_type` ∈ [첨부3] 코드
- [ ] `saving_method` ∈ {`01`,`02`,`03`,`04`}
- [ ] `trans_type` ∈ {`01`~`07`,`98`,`99`}
- [ ] `repay_method` ∈ [첨부4] 코드
- [ ] `account_status` == `"01"`
- [ ] `account_type`과 `saving_method` 조합이 5.2 표와 일치하는가

### 11.5 날짜 형식

- [ ] `DATE` 필드가 `YYYYMMDD` 8자리 문자열인가
- [ ] `DTIME` 필드가 `YYYYMMDDhhmmss` 14자리 문자열인가
- [ ] `unredeemed_*`가 `YYYYMM` 6자리인가
