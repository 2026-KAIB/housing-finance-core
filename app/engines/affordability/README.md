# Property affordability engine v1

검색된 매물 한 건마다 다음 값을 같은 기준일로 결합한다.

```text
최소 필요자금 = 매물가 + 현재 확인된 구매부대비용
사용 가능 자기자금 = 유동자산 - 비상자금 목표
필요 대출금액 = 필요자금 - 사용 가능 자기자금
자금 부족액 = 필요자금 - 자기자금 - 실행 가능한 대출 조합
```

`app.services.property_affordability`가 구매부대비용 엔진, 현금흐름 엔진,
규제지역 판정, 대출 옵션 계산과 대출 조합 엔진을 호출한다. 최종 판정 엔진은
그 계산 결과만 받아 순수하게 동작하며 DB나 JSON 파일을 직접 읽지 않는다.
검색 JSON의 `PropertyCandidate`는 `build_property_affordability_case()`에 넘기면
가격과 전용면적을 구매부대비용 입력으로 그대로 복사하므로 중복 입력 불일치를
막을 수 있다. 주택 등재 여부·고급주택 여부처럼 매물 JSON에 아직 없는 법적 사실은
추측하지 않고 별도 인자로 받는다.

## 판정

- `AFFORDABLE`: 총비용이 확정됐고 자기자금과 대출 조합으로 조달 가능
- `TIGHT`: 조달은 가능하지만 허용오차에 의존하거나, 스트레스 월 잉여가
  현금흐름 Buffer보다 작거나, 비상자금 목표가 충분히 보호되지 않음
- `SHORTFALL`: 현재 확인된 최소 비용만으로도 허용오차를 넘는 자금 부족
- `UNKNOWN`: 부대비용·지역·대출 후보 등 필수 입력이 미확정
- `UNSUPPORTED`: 법인·다주택·고급주택 등 구매부대비용 v1 지원 범위 밖

부분 비용 결과의 `minimum_total_purchase_cost`를 최종 총액처럼 사용하지 않는다.
최소 비용조차 조달하지 못하면 `SHORTFALL`은 확정할 수 있지만, 최소 비용을
조달할 수 있다는 이유만으로 `AFFORDABLE`을 반환하지 않고 `UNKNOWN`으로 남긴다.

## 조합 경계

- 매물의 `sigungu_code`로 규제지역과 DTI 지역을 다시 결정한다.
- 대출의 `required_amount`와 Rule Pack의 `requested_amount`를 매물별 필요금액으로
  덮어쓴다.
- 대출 후보가 전달되지 않은 상태를 “가능한 상품 없음”으로 해석하지 않는다.
- 비상자금은 필요자금에 다시 더하지 않고 유동자산에서 먼저 보호한다. 두 방식은
  같은 제약을 표현하지만 동시에 사용하면 비상자금을 이중 차감하게 된다.
